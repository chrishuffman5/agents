# MCP spec revision 2026-07-28 (release candidate / draft)

Read this only when the user explicitly targets the draft revision or is reading draft documentation. Do not mix these shapes with `2025-11-25` code — the handshake and several primitives differ.

## Status

> Source: https://modelcontextprotocol.io/specification/2025-11-25
> Source: https://modelcontextprotocol.io/docs/learn/architecture

**2026-07-28 is a release-candidate / draft revision** as of 2026-08-05. `2025-11-25` remains the stable revision for production. Anything in this file is subject to change before the draft is finalized.

## Deltas from 2025-11-25

> Source: https://modelcontextprotocol.io/docs/learn/architecture

### Discovery handshake replaces initialize-once

Adds a mandatory **`server/discover`** request replacing/augmenting the old `initialize` handshake style, with per-request `_meta` fields carried on **every** request rather than only at session start:

- `io.modelcontextprotocol/protocolVersion`
- `io.modelcontextprotocol/clientInfo`
- `io.modelcontextprotocol/clientCapabilities`

Results carry a `resultType` field (e.g. `"complete"`).

```json
{
  "jsonrpc": "2.0", "id": 2, "method": "tools/list",
  "params": { "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientInfo": {"name":"example-client","version":"1.0.0"},
    "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}
  } }
}
```

Method names (`tools/list`, `tools/call`) and the `inputSchema` / `content` shapes are **unchanged** from stable; only the envelope differs.

### Deprecations

> Source: https://modelcontextprotocol.io/docs/learn/client-concepts

- **Sampling** — deprecated, scheduled for removal. New implementations should integrate directly with LLM provider APIs.
- **Roots** — deprecated, scheduled for removal. Pass directories via tool parameters, resource URIs, or server configuration instead.
- **Logging** — deprecated in favor of `stderr` (for stdio servers) or OpenTelemetry.

**Elicitation is not deprecated** and remains the supported way for a server to request user input.

### Generalized subscriptions

`subscriptions/listen` becomes a general opt-in notification-subscription mechanism, replacing ad hoc `resources/subscribe`.

```json
// Client opens a subscription
{ "jsonrpc":"2.0","id":4,"method":"subscriptions/listen","params":{ "_meta": {}, "notifications": {"toolsListChanged": true} } }
// Server ack (first message, carries subscriptionId)
{ "jsonrpc":"2.0","method":"notifications/subscriptions/acknowledged","params":{ "_meta":{"io.modelcontextprotocol/subscriptionId":4}, "notifications":{"toolsListChanged":true} } }
// Server later sends, on change:
{ "jsonrpc":"2.0","method":"notifications/tools/list_changed","params":{ "_meta":{"io.modelcontextprotocol/subscriptionId":4} } }
```

Resource watching uses the same mechanism with a `resourceSubscriptions` field naming the URIs; the server then delivers `notifications/resources/updated` on the resulting stream. Delivery remains **best-effort** — clients should still poll to guarantee freshness, especially across transport reconnects.

### Multi Round-Trip Requests (MRTR) and `InputRequiredResult`

> Source: https://modelcontextprotocol.io/docs/learn/client-concepts

Introduces an `InputRequiredResult` / MRTR pattern used by both elicitation and (deprecated) sampling. A server needing input while processing `tools/call` responds with an `InputRequiredResult` whose `inputRequests` field carries one or more `elicitation/create` (or `sampling/createMessage`) requests. The client gathers input and **retries the original request**, attaching `inputResponses` and echoing back any `requestState` the server included.

```
Client -> Server: tools/call (id: 1)
Server -> Client: InputRequiredResult { inputRequests: [elicitation/create] }
Client -> User: present elicitation UI
User -> Client: provide info
Client -> Server: tools/call (id: 2, inputResponses)
Server -> Client: final result
```

### Caching hints

`tools/list` responses may carry `ttlMs` and `cacheScope` (e.g. `"public"`) as part of a draft-only caching utility.

### Extensions mechanism

Adds an extensions mechanism documented separately from the core spec — for example the **Tasks extension** for long-running requests.

## Migration guidance

- Do not adopt `server/discover` or per-request `_meta` unless the counterparty is confirmed on `2026-07-28`; a stable-revision peer will not understand them.
- If a codebase still relies on sampling or roots, plan replacements now (direct provider API calls; directories via tool parameters) — both are scheduled for removal.
- Replace stdio-server logging that used the MCP logging utility with plain `stderr` writes or OpenTelemetry.
